1. Deadlock Demonstration:
The fourth experiment demonstrated how a deadlock can occur when two models
request shared GPUs in different orders. Model A acquired GPU 0 first, while
Model B acquired GPU 1 first. After `sleep(0.1)`, Model A requested GPU 1 and
Model B requested GPU 0. Each model was waiting for a GPU held by the other,
so a circular wait occurred. The program had no recovery mechanism and was
stopped after one second.

2. Deadlock Avoidance:
The deadlock was avoided by making both models request the GPUs in the same
order: GPU 0 followed by GPU 1. If Model A acquired GPU 0, Model B waited for
GPU 0 without holding GPU 1. Model A could then acquire GPU 1, finish, and
release both resources. This removed the circular wait condition.

3. Starvation vs. Deadlock:
The starvation experiment showed a different problem. After three seconds,
all threads had made some progress, but the two greedy models acquired the
resource about 24,000 times each while `Polite_Model` acquired it only 297
times. This was unfair, but it was not a deadlock because the threads were
still able to continue. An aging scheduler could increase the priority of a
process that had waited for a long time, giving `Polite_Model` a fairer chance
to run.

4. Deadlock Detection and Recovery:
Finally, `timeout=2.0` simulated deadlock detection by limiting Model A's
wait for GPU 1. When the timeout expired, an OS watchdog treated the wait as
a deadlock instead of allowing the program to wait forever. Model A then
released GPU 0 and stopped, breaking the cycle. Model B could acquire GPU 0,
finish its work, and release its GPUs, allowing the system to complete.
