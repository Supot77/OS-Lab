1. The Race Condition (Phase 2):
The final weight is too low because changing the shared value uses three
steps: read, add one, and write. Two threads can read the same value at the
same time. They then both write the same new value, so one update replaces
the other. In the test, the expected value was 200 but the actual value was
101.

The very short `time.sleep(0.0000001)` gives the OS scheduler a chance to
switch to the other thread between the read and write steps. This timing
causes the lost updates and shows the race condition.

2. Mutex vs. Semaphore (Phase 3):
The `mutex` protects the buffer. It allows only one thread at a time to
change the buffer, `in_index`, or `out_index`.

The `empty` semaphore counts free spaces in the buffer. The producer takes
one before adding an item and waits when the buffer is full. The `full`
semaphore counts items ready to read. The consumer takes one before reading
and waits when the buffer is empty. A mutex only controls one thread's access
at a time. It cannot count free spaces or items, so it cannot replace both
semaphores.

3. Deadlock Awareness:
If the producer took the `mutex` first while the buffer was full, it would
wait for an empty slot while still holding the mutex. The consumer would need
the mutex to remove an item and create an empty slot, but it could not get the
mutex. Both threads would wait forever. Taking `empty` first lets the
producer wait without holding the mutex, so the consumer can continue.
